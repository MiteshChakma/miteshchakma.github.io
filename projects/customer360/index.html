Why this was made

Purpose of the project

This project was created as a simple, reviewable portfolio example for data engineering roles. It demonstrates practical fundamentals: reading raw source data, validating schemas, loading a local warehouse, writing SQL transformations, creating a Customer 360 data product, testing the pipeline, and training a small local model from the generated features.

The implementation intentionally uses SQLite instead of a cloud warehouse. That keeps the project honest, runnable on a laptop, and easy for visitors to inspect without credentials or paid services.

Scenario design

How the example maps to a real business problem

The project simulates a small retail company that wants to understand customers across multiple operational systems. In a real company, customer profile data may come from a CRM, order data from an ecommerce platform, web events from analytics tracking, and support tickets from a helpdesk tool. The purpose of this demo is to model that same situation locally with four small CSV files.

The data was prepared as synthetic sample data with deliberate relationships between tables. Every source uses customer_id as the join key, orders include both completed and returned transactions, web events include checkout behavior, and support tickets include priority and resolution time. These fields were chosen because they are realistic signals for a Customer 360 product.

Data assumptions

Each customer has one profile row. Orders, web events, and support tickets can contain multiple rows per customer. The project assumes customer_id is stable across all sources.

Business assumptions

Completed orders count toward revenue. Returned orders are tracked but excluded from revenue. High-priority support issues and weak checkout behavior are treated as churn-risk signals.

Engineering assumptions

The pipeline should be repeatable, local, and easy to inspect. SQLite is used as the warehouse layer because it supports SQL transformations without external setup.

Beginner guide

How to implement the project from beginning to end

This guide explains the whole project as if you are rebuilding it yourself. The project is intentionally small, but the same thinking applies to larger pipelines: understand the problem, define source data, validate inputs, transform with SQL, export a data product, train a downstream model, and test the workflow.

Before coding: understand the codebase layout

A beginner should first know which file is responsible for which part of the work. This project separates data, SQL, Python pipeline code, model code, and tests so each responsibility is easy to find.

data/raw/

Stores the four synthetic source CSV files. These are the inputs to the pipeline.

src/customer360/cli.py

Command-line entrypoint. This is the file indirectly executed when running python -m customer360.cli build.

src/customer360/pipeline.py

Main orchestration. It reads CSVs, calls validation, loads SQLite, runs SQL, and writes the final CSV.

src/customer360/validation.py

Schema and data quality rules for raw sources and the exported Customer 360 file.

sql/customer_360.sql

SQL transformation layer. It aggregates raw tables into the final customer_360 table.

src/customer360/ml/train.py

Local machine-learning workflow. It trains a scikit-learn model and writes model artifacts.

tests/

Automated checks for validation, pipeline output, revenue rules, churn labels, and model artifacts.

build/

Generated outputs: SQLite database, Customer 360 CSV, metrics JSON, and trained model file.

Stage 0: Understand the business problem

Why?

A Customer 360 table gives analysts and downstream systems one trusted row per customer. Without it, customer information stays scattered across orders, web activity, and support systems.

What?

The project creates a customer-level dataset that answers: who spends the most, who has support issues, who is active on the website, and who may be at churn risk.

How?

Start with a small problem statement, then list the source files and the final fields you want in the output. In this project, the final output is build/customer_360.csv.

Stage 1: Prepare the source data

Why?

Every pipeline starts with source data. A novice mistake is writing code before understanding what each column means. Good data engineering starts with knowing the input shape.

What?

The project uses four synthetic CSV files: customers.csv, orders.csv, web_events.csv, and support_tickets.csv. The data was created by ChatGPT for this portfolio project.

How?

Place the files under data/raw/. Keep one file per source concept, use a stable key such as customer_id, and document the columns before writing transformations.

customer360-data-engineering-demo/
  data/raw/customers.csv
  data/raw/orders.csv
  data/raw/web_events.csv
  data/raw/support_tickets.csv

Files to inspect: data/raw/customers.csv, orders.csv, web_events.csv, and support_tickets.csv.

Implementation reason: source files stay separate from generated outputs so the pipeline can be rerun from the same raw inputs.

Tech used: CSV files because they are simple, portable, and easy for reviewers to open.

Expected output: no generated file yet; the checkpoint is that all four CSV files exist and share the customer_id key.

Stage 2: Ingest CSV files with Python

Why?

Ingestion is the step where raw files enter the pipeline. Keeping ingestion separate from validation and transformation makes the code easier to test and maintain.

What?

The pipeline reads each CSV into a pandas DataFrame. The file-to-table mapping is defined once so the same names are reused consistently.

How?

The Customer360Pipeline class reads files from data/raw. If you add a new source file later, you update the source mapping and validation rules.

RAW_TABLES = {
    "customers": "customers.csv",
    "orders": "orders.csv",
    "web_events": "web_events.csv",
    "support_tickets": "support_tickets.csv",
}

File to run: src/customer360/cli.py through python -m customer360.cli build --data-dir data/raw --output-dir build.

Code path: cli.py creates Customer360Pipeline, then pipeline.py calls _read_sources().

Reasoning: the CLI hides implementation details from the user while keeping the pipeline reusable from tests or other Python code.

Expected output: four pandas DataFrames in memory, one for each raw source table; this step continues automatically into validation during the build command.

Stage 3: Validate schemas and basic quality

Why?

Validation prevents broken or unexpected data from silently producing wrong analytics. If a required column is missing, the pipeline should fail early.

What?

This project checks that each source table has required columns, order amounts are not negative, and order status values are limited to completed or returned.

How?

Validation logic lives in src/customer360/validation.py. It raises clear errors when data does not match the expected schema.

validate_raw_sources(frames)

# Example checks:
# - required columns exist
# - order_amount is non-negative
# - status is completed or returned

File written for this stage: src/customer360/validation.py.

Design reason: validation is separated from ingestion so the rules can be tested independently with small DataFrames.

File to run: validation runs automatically during python -m customer360.cli build; after building, run python -m customer360.cli validate --customer360 build/customer_360.csv to check the exported file.

Expected output: valid data continues into SQLite; invalid data raises a readable ValueError. The standalone validation command prints Customer 360 schema validation passed.

Stage 4: Load raw data into SQLite

Why?

SQLite gives the project a real SQL layer without requiring a remote warehouse. It lets a reviewer inspect tables and transformations locally.

What?

Each DataFrame is written to a SQLite table named after the source: customers, orders, web_events, and support_tickets.

How?

The pipeline opens build/customer360.db and uses pandas to_sql to replace the raw tables on each run. This keeps local runs repeatable.

with sqlite3.connect("build/customer360.db") as conn:
    frame.to_sql(table_name, conn, if_exists="replace", index=False)

File written for this stage: src/customer360/pipeline.py.

Why SQLite: it behaves like a real SQL database but runs locally from one file, which is ideal for a portfolio demo.

File to run: this is part of python -m customer360.cli build --data-dir data/raw --output-dir build.

Expected output: build/customer360.db is created. Inside it, the raw tables are loaded before the final mart table is built.

Stage 5: Transform raw tables into Customer 360 SQL features

Why?

The main value of the project is the transformation from many activity rows into one useful customer row. This is the heart of Customer 360 data modeling.

What?

The SQL calculates completed order count, revenue excluding returned orders, return count, web sessions, checkout events, support ticket count, average resolution time, high-priority support flags, and a simple churn label.

How?

The transformation is written in sql/customer_360.sql. It uses common SQL patterns: grouped feature CTEs, LEFT JOIN, COALESCE, CASE, and aggregation.

CASE
    WHEN completed_orders <= 1
      AND checkout_events = 0
      AND had_high_priority_ticket = 1
    THEN 1
    ELSE 0
END AS churn_label

File written for this stage: sql/customer_360.sql.

Code path: pipeline.py calls conn.executescript(...) to run the SQL file against SQLite.

Reasoning: SQL keeps aggregation logic readable and close to how a real warehouse mart would be built.

Expected output: a new SQLite table named customer_360 with one row per customer.

Stage 6: Export the Customer 360 data product

Why?

A pipeline should produce a clear artifact. Here, the artifact is a CSV that can be inspected, shared, or used by the model training step.

What?

The output file build/customer_360.csv contains one row per customer and 15 fields covering profile, revenue, behavior, support, and churn label.

How?

After the SQL creates the customer_360 table, Python reads that table back from SQLite and writes it to CSV.

customer360 = pd.read_sql_query(
    "SELECT * FROM customer_360 ORDER BY customer_id",
    conn,
)
customer360.to_csv("build/customer_360.csv", index=False)

File written for this stage: src/customer360/pipeline.py.

Why export CSV: it makes the data product visible without special tooling and gives the ML script a simple input.

File to run: python -m customer360.cli build --data-dir data/raw --output-dir build.

Expected output: terminal prints Customer 360 rows: 6, and build/customer_360.csv contains 6 rows and 15 columns.

Stage 7: Train a small local model from the output

Why?

Many data engineering pipelines feed analytics or machine learning. This step shows that the generated Customer 360 table can be consumed by a downstream ML workflow.

What?

The training script reads customer_360.csv, prepares categorical and numeric features, trains a small scikit-learn classifier, and writes model artifacts.

How?

Run the training module after the pipeline build. The output files are build/churn_model.joblib and build/model_metrics.json.

python -m customer360.ml.train \
  --input build/customer_360.csv \
  --model-dir build

File to run: src/customer360/ml/train.py through python -m customer360.ml.train --input build/customer_360.csv --model-dir build.

Tech used: scikit-learn ColumnTransformer, OneHotEncoder, RandomForestClassifier, and joblib.

Reasoning: the model is intentionally simple because the goal is to demonstrate how a data product feeds ML, not to claim production model quality.

Expected output: terminal prints {"accuracy": 1.0, "roc_auc": 1.0} for this tiny synthetic dataset, and creates build/churn_model.joblib plus build/model_metrics.json.

Stage 8: Test the pipeline

Why?

Tests prove that the pipeline is repeatable and that important rules do not break silently when code changes.

What?

The tests check schema validation, end-to-end pipeline output, revenue handling for returned orders, binary churn labels, and model artifact creation.

How?

Run pytest from the project folder. A successful run means the local pipeline, validation, and model workflow are working together.

pytest -q

# Expected result:
# 3 passed

Files to run: tests/test_validation.py, tests/test_pipeline.py, and tests/test_train.py through the pytest command.

Design reason: tests prove the project is not just a static demo; it can rebuild outputs and verify important rules automatically.

Expected result: the terminal shows 3 passed.
